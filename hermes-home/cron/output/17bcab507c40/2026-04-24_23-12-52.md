## Key 静默失效：最危险的漏报模式（2026-04-24 发现）

**⚠️ HTTP 200 ≠ Key 正常。Key 可能返回 200 但 `results=[]`。**

### 根因
代理（SOCKS5H）间歇性 SSL 重置（`SSLZeroReturnError`）导致连接被意外关闭。
Tavily 库层的异常处理会触发重试→换 key，但如果**某次请求恰好成功建立连接**，
服务器返回 200 但结果为空（网络层已断），此时**不触发任何 exhausted 标记**。

### 症状
```
state.json: exhausted: [true, true, true, true]  ← 全灭！
实测: Key2 curl → HTTP 200, results: 0  ← 静默失败
```

### 排查步骤

## 关键发现（经验总结 2026-04-22）

### ✅ MiniMax 不需要代理！
**代理（`127.0.0.1:7890`）会导致 MiniMax API 超时，直连反而快且稳定。**
生图 API 和 OSS 图片下载都**不要走代理**，全部直连。

### ✅ 两个端点均可用（同一个 token）
- `https://api.minimax.chat/v1/image_generation`（推荐，新版）
- `https://api.minimaxi.com/v1/image_generation`（旧版）

两者返回格式完全一致，同一个 token 通用。

### ✅ ANTHROPIC_AUTH_TOKEN 就是 MiniMax key
shell 里 `echo $ANTHROPIC_AUTH_TOKEN` 显示为 `sk-cp-...`，这就是 MiniMax API key。Bearer token 直接用这个。
**注意：`execute_code` sandbox 会把 ANTHROPIC_AUTH_TOKEN 脱敏成 `***...`，但在 terminal/shell 环境完全正常。**

### ❌ FEISHU_BOT_TOKEN 是错的！
环境中没有 `FEISHU_BOT_TOKEN` 这个环境变量。**飞书图片上传需要 tenant_access_token**，必须通过以下方式获取：
```python
app_id = os.environ['FEISHU_APP_ID']
app_secret = os.environ['FEISHU_APP_SECRET']
r = requests.post(
    'https://open.feishu.cn/open-apis/auth/v3/tenant_access_token/internal',
    json={'app_id': app_id, 'app_secret': app_secret}
)
feishu_token = r.json()['tenant_access_token']
```

### ⚠️ API 响应格式注意
MiniMax 图片生成 API 响应格式：
```json
{
  "data": {
    "image_urls": ["https://...", "https://..."]  // 不是 data[0]["url"]！
  }
}
```
正确的访问方式：`resp.json()["data"]["image_urls"][0]`

### ⚠️ 飞书上传 files 参数格式
正确格式（**三元组 tuple**）：
```python
files = {
    'image_type': (None, 'message'),          # filename=None, content='message'
    'image': ('attosecond.jpg', open(path, 'rb'), 'image/jpeg')  # filename, file, mime
}
```
错误格式（会 400 Bad Request）：
```python
files = {'image_type': 'message', 'image': open(path, 'rb')}  # ❌ 二元组
files = {"image_type": ("message", open(path, "rb"), "image/jpeg")}  # ❌ key名错
```
**核心：image_type 和 image 都在 files dict 里，image_type 元组第一元素为 None！**

### ⚠️ MiniMax OSS 图片 URL 需要 URL decode
MiniMax 返回的 URL 含有 `%2F` 等编码字符（OSS 签名URL），直接 `requests.get()` 可能 403。
**必须用 `urllib.parse.unquote()` 先解码再下载：**
```python
from urllib.parse import unquote
image_url = unquote(data["data"]["image_urls"][0])  # 先解码！
img = requests.get(image_url, timeout=30)  # 再下载
```

## 飞书卡片 API 关键坑
### ❌ 错误：双 JSON 编码导致乱码（9499 错误）

飞书 API 两次接收 `content` 字段：**第一次**在 `requests.post(json=...)` 或 `urllib.request.urlopen()` 调用时，Python 库自动把整个 `payload` dict 序列化成 JSON 字符串；**第二次**飞书服务器内部再解析 `content` 字段。

如果 `content` 本身已经是 JSON 字符串（提前 `json.dumps` 过了），飞书会拿到被转义两层的字符串 → 9499 Bad Request。

```python
# 错：content 放 Dict → requests.post(json=payload) 编码一次 → content 变成转义字符串
payload = {"receive_id": chat_id, "msg_type": "interactive", "content": card_dict}
requests.post(url, json=payload, ...)  # 9499 — content 被双重编码
```

**正确做法：`content` 必须预先 dumps 成字符串，outer body 用 `data=json.dumps(...)` 只编码一次：**

```python
import requests, json

# content 必须是预编码的 JSON 字符串！
payload = {
    "receive_id": chat_id,
    "msg_type": "interactive",
    "content": json.dumps(card, ensure_ascii=False)  # STRING，不是 dict
}
response = requests.post(
    url,
    data=json.dumps(payload, ensure_ascii=False),   # outer 也 dumps，但 content 已是字符串
    headers={"Authorization": f"Bearer {token}", "Content-Type": "application/json"},
    timeout=30
)
```

**验证方法**：飞书开发者工具查看卡片原始 JSON，`content` 字段值应以 `{` 开头而非 `\"` 开头。9499 错误响应体的 `Invalid parameter value` 会显示被双重编码的内容。

### background_style 值限制
仅支持基础色：`blue`, `purple`, `orange`, `grey`, `red`, `wathet`, `turquoise`
**不支持** `blue-50`、`blue-70` 等带数字后缀格式。

### ❌ hr 标签不支持 color 属性
`<hr color="grey">` 在飞书卡片中不生效，不要使用。

### ❌ 禁止在卡片内嵌套 `tag: card`
飞书不支持嵌套卡片（会报 200621 "not support tag: card"）。底部统计栏用 `hr` + `markdown`居中块代替，不要用嵌套 `card` 包裹。

### ❌ `<font color>` 标签导致乱码
**所有 `<font color=...>` 一律用 markdown 加粗替代**，不加区分颜色。乱码原因：飞书 Markdown 解析器对 `font` 标签的编码处理不稳定。

```python
# ❌ 全部禁止
"<font color='blue'>📚 {n} 篇</font>"
"<font color='green'>⬆️ {c} 引用</font>"
"<font color='grey'>暂无数据</font>"
"<font color='white' fill='blue'> {idx} </font>"

# ✅ 正确做法：用 markdown 加粗
f"📚 **{n}** 篇"
f"⬆️ **{c}** 引用"
"📂 暂无数据"
f"**{idx}**"
```

**全面排查清单**（用 `grep "font color" optics_tracker_v2.py` 验证）：
- `count_badge` 论文数量徽章
- `stats_parts` 顶部统计栏（蓝/绿/橙/红）
- `badge` 论文序号徽章（white+fill）
- `button` 暂无数据后备文字（grey）
- `_build_paper_content` 返回值外层包裹（grey）

`<font color='grey'>` 包裹的文字在白色背景卡片上对比度极差，肉眼几乎看不见。

**必须排查的所有 grey 位置（都要去掉）：**
1. `build_domain_cell` 中的 `trend_text`（趋势文字）
2. `_build_6dimension_content` 返回时的外层包裹（6维度分析内容）

```python

return f"<font color='grey'>{content}</font>"

# ✅ 对：直接返回内容，不用 grey 包裹
```

### ⚠️ LaTeX 数学公式导致乱码

### ❌ `_merge_paper` 静默丢弃 `analysis` 字段

Phase 1 合并多源论文时，`_merge_paper` 只比较 authors / abstract / citations，不保留 `analysis`。如果同一篇论文先被 Tavily 分析（带 `analysis`），再被 ArXiv 收录（无 `analysis`），**后者覆盖前者，`analysis` 丢失**。

```python

result["authors"]  = new if len(new) > len(existing)
result["abstract"] = new if len(new) > len(existing)
result["citations"] = new if new > existing
```

**症状**：某领域只有 1 篇论文带 analysis，但明明收集了多源结果。

**诊断**：打印合并前后 `p.get("analysis")` 对比。

**修复**：`card_data/laser_processing.json` 这种残留旧 analysis 的缓存，每次调试前手动删除。

### ❌ laser_processing 领域今日 0 篇的原因

**双重叠加**：
1. ArXiv 只召回到 9 篇（关键词命中率低），且 Tavily API 432 失败，该领域完全依赖 ArXiv。
2. 3 篇 ArXiv 论文的 MiniMax 6维分析全部 `Parse analysis failed`（摘要格式不符预期）。
3. 残留 Tavily 论文的旧 analysis 也在合并时被丢弃（见上条）。

**结论**：不是信源问题，是 MiniMax 解析率问题。需要在 `batch_analyze` 后对 analysis dict 做字段完整性检查（至少 4/6 字段），不足则视为失败。

### .pyc 缓存导致 MiniMax 解析失败的 Bug

**症状**：`_parse_analysis` 代码已更新，但发送的卡片 6 维度内容仍全是乱码或解析失败。

**根因**：Python 的 `.pyc` 缓存优先于 `.py` 源文件加载，导致新代码未生效。

**排查**：检查 `__pycache__/` 下 `.pyc` 文件 mtime 是否比 `.py` 新。若新，说明 Python 加载的是旧缓存。

**修复**：每次修改 `optics_tracker_v2.py` 后，必须清 `__pycache__/` 再运行：
```bash
# 改代码后必须执行
find . -name "*.pyc" -delete
find . -name "__pycache__" -type d -exec rm -rf {} +
python3 optics_tracker_v2.py --feishu --category nearfield_optics --fast
```

### ❌ 近场光学论文数量不符（6篇显示成3篇）

**根因**：`near field` 不加引号，ArXiv 被拆成 `near AND field`，匹配到大量量子信息/超表面论文。

**修复方案**：多级短语匹配
- 单单词：`ti:kw OR abs:kw`
- 多单词/带空格：`all:"near field"`
- 连字符词：`all:"near-field"`（若 hyphen 两端单词较短也加引号）

```python
def _should_quote(kw: str) -> bool:
    """多单词或短连字符词需要加 all:\"...\" 短语匹配"""
    if " " in kw:
        return True
    if "-" in kw:
        parts = kw.split("-")
        # 如果任意一段很短（<4字符），两端拼接会混淆
        if any(len(p) < 4 for p in parts):
            return True
    return False
```
